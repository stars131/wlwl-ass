# Research SOP

## 触发

用户给出一个概念、名称、公司、岗位、产品、人物、事件或市场问题，并希望“全网调研”“深度研究”“行业报告”“竞品分析”“岗位/技术/市场画像”时使用本 SOP。

若主题涉及 OpenAI、岗位、公司、价格、招聘、政策、新闻、标准、产品能力等可能变化的信息，必须联网核验当前状态，并在报告中标注检索日期。

## 目标产物

默认产出两类文件：

- SOP/模板复用：`memory/research_sop.md` 与 `memory/research_report_template.md`
- 单次报告：`temp/research_reports/YYYY-MM-DD_<slug>.md`

报告必须能回答：

- 这是什么：定义、边界、同义词、反义词、常见误解。
- 为什么重要：行业驱动、需求变化、成本/收益、采用门槛。
- 谁在做：关键公司、生态角色、招聘/产品/资本/开源信号。
- 怎么判断真假：证据强度、冲突证据、不可验证项。
- 对用户有什么用：行动建议、风险、下一步验证。

## 严谨性门槛

单次调研结束前，至少满足以下门槛；无法满足时必须在报告中写明缺口。

- 一手证据：至少 2 个来自目标主体、官方文档、招聘页、监管文件、论文、代码库、数据集或原始公告的来源。
- 独立交叉验证：每个关键结论至少由 2 个独立来源支撑；只有单一低可信来源支撑的内容只能列为“线索”。
- 时间标注：所有可能变化的事实必须带日期或“截至 YYYY-MM-DD”。
- 反向搜索：必须搜索否定词、替代词和冲突词，例如 `criticism`, `rebrand`, `fake`, `controversy`, `vs`, `alternative`, `招聘`, `裁撤`, `薪资`。
- 证据台账：报告末尾必须列出来源、类型、用途、可信等级、访问日期。
- 不确定性：禁止把招聘博客、社媒贴、SEO 文章中的数字直接写成事实；必须标成二级/三级证据。

## 证据分级

- A 级：目标主体官网、官方招聘页、官方博客、监管文件、法院/政府数据、论文原文、项目源码、公司财报、标准文档。
- B 级：权威媒体、专业分析机构、招聘平台聚合数据、行业报告、可信作者的长文。
- C 级：普通博客、SEO 内容、论坛、社交媒体、二手转述、未经公开方法说明的数据。

可信度标注：

- 高：A 级来源直接证明，且无冲突证据。
- 中：A+B 或多个 B 级来源一致，但关键细节仍依赖解释。
- 低：仅 C 级或单一来源，适合作为假设或线索。

## 流程

### 1. 明确研究问题

把用户输入拆成 3-7 个问题：

- 定义问题：这个词/对象的准确含义是什么？
- 事实问题：当前有哪些官方证据？
- 市场问题：谁在采用，规模/趋势如何？
- 结构问题：角色、商业模式、技术栈、流程或组织关系是什么？
- 决策问题：用户应如何判断、学习、招聘、投资、采用或规避？

### 2. 设计检索矩阵

每个主题至少覆盖这些查询族：

- 精确词：`"<原词>"`, `"<英文名>"`, `"<缩写>"`
- 官方源：`site:<official-domain> "<term>"`
- 招聘源：`"<term>" careers job compensation`
- 市场源：`"<term>" market trend adoption`
- 技术源：`"<term>" architecture github paper`
- 反证源：`"<term>" criticism risk failure rebrand`
- 中文源：`"<term>" 中文 介绍 招聘 薪资`

同时使用至少两种检索路径，例如普通网页搜索、Tavily、目标站点搜索、GitHub/论文/招聘站点。

### 3. 技能与外部方法试用

先查本地可用 SOP/技能：

```powershell
python -m skill_search "<topic> research" --top 5
python -m skill_search "<中文关键词> 调研 报告" --top 5
```

若找到外部 GitHub skill、OSINT 方法、报告模板或脚本：

- 先只读，不执行不明脚本。
- 检查许可证、维护状态、最近提交、issue、依赖、是否要求密钥。
- 用小样本验证是否提升质量或效率。
- 只有在确实可复用、低风险、与本仓库目标一致时，才沉淀到 `memory/` 或技能目录；否则只在报告的“技能试用记录”中说明未保留。

### 4. 采集与证据台账

为每条证据记录：

- URL
- 标题
- 发布/更新日期
- 访问日期
- 来源类型与等级
- 支撑的结论
- 摘要
- 限制或冲突点

对网页内容避免长段复制；使用自己的话总结，只保留必要短引文。

### 5. 分析框架

根据主题选择框架，岗位/概念类默认使用：

- 定义与边界
- 发展脉络
- 需求驱动
- 代表组织/案例
- 工作流或系统结构
- 能力模型
- 经济性与激励
- 风险与反例
- 对目标读者的行动建议

公司/市场类可增加：

- 市场规模与增长
- 价值链
- 竞争格局
- 商业模式
- 监管/合规
- 投资与并购
- 机会窗口

技术类可增加：

- 架构
- 依赖与生态
- 性能/成本
- 安全边界
- 替代方案
- 迁移路径

### 6. 写作规范

报告开头必须有“结论先行”：

- 一句话定义
- 3-7 条关键发现
- 可信度评级
- 对用户最有用的行动判断

正文必须区分：

- 已证实事实
- 强推断
- 弱信号
- 未验证/待跟进

不要把所有来源等权处理。官方招聘页证明岗位要求；博客只能解释趋势或提供可验证线索。

### 7. 红队检查

提交前问自己：

- 是否有同名词导致歧义？
- 是否把历史页面当成当前状态？
- 是否把“招聘中”误写成“已大规模落地”？
- 是否把媒体估算当成官方数字？
- 是否只看支持材料，没有看反证？
- 是否有重要地域差异、薪资口径差异、监管差异？
- 是否有过时页面、404 页面或搜索摘要无法复核？

### 8. 完成审计

完成报告前逐项检查：

- 研究问题都有明确回答或缺口说明。
- 核心结论都有来源支撑。
- 来源链接可访问，或已标注访问失败/404。
- 当前性事实已联网核验。
- 已记录检索词、工具、技能试用结果。
- 已写出下一步更高强度验证方法，例如访谈、爬取招聘样本、薪酬数据库、专家审阅。

## 报告命名

文件名使用：

```text
temp/research_reports/YYYY-MM-DD_<topic-slug>.md
```

示例：

```text
temp/research_reports/2026-05-22_fde_forward_deployed_engineer.md
```

## 方法参考

- SIFT/lateral reading：强调停止、调查来源、寻找更好覆盖、回到原始语境。
- CRAAP：从时效、相关性、权威性、准确性、目的性评估来源。
- OSINT cycle：界定范围、采集、处理、分析、验证、报告。
